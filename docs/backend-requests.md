# 팀 확인 및 백엔드 추가 데이터 요청

기존 백엔드 코드는 수정하지 않았고 이슈·메시지를 외부로 전송하지 않았습니다. 아래는 전달용 요청 목록입니다.

| 우선순위 | 확인/요청 | 현재 한계와 필요한 이유 |
| --- | --- | --- |
| 필수 | 운영 API base URL, 합의된 테스트 계정/세션 제공 방식 | 운영 연결 및 실제 응답 검증 미실시. 세션은 개인 비밀값으로 공유 문서에 넣지 않음 |
| 필수 | 동방 전체와 공간/테이블의 대응, 중복 없는 전체 정원 | capacity 자동 합산은 전체 방+테이블 중복 가능. attendance는 방 전체만 제공 |
| 필수 | 일정/참여자 과거 데이터 완전 보존 시작일과 보존 정책 | 빈 응답이 과거 무예약인지 기록 누락인지 알 수 없음. 확인 전 과거 통계 사용 안 함 |
| 필수 | 동방 운영/방문 가능 시간 | API에 운영 시간 없음. 현재 결과는 하루 전체 분석이며 방문 가능을 보장하지 않음 |
| 권장 | 일정 기간 조회 및 페이지/배치 participants 조회 | 현재 모든 미취소 일정과 각 참여자를 N+1 조회. 데이터 증가 시 성능 문제 |
| 권장 | 일관된 스냅샷 시각/버전, 참여자 변경 버전 | 여러 요청 중 일정·참여 상태가 달라질 수 있음 |
| 권장 | occupancy 응답의 server_as_of, 최종 변경 시각, 기록 보정 정책 | 현재 current_count/revision만 존재. 요청 시각만 기록 가능; 미퇴실 기록 보정 불명 |
| 권장 | 일정 및 참여 변경 이력 또는 일별 마감 스냅샷 | 현재 과거 취소·참여 취소 내역을 복원할 수 없어 당시 상태 통계는 불가 |
| 선택 | 구조화된 인원 제보(count, observed_at, scope, source, 검증 상태) | 일반 채팅은 인원 데이터가 아님. 명시적 제보도 전체 방/시간/진위 불명. 기본 수치 반영 꺼짐 |
| 선택 | 실제 방문 대비 예약·제보 정확도 검증 자료 | 현재 신청 기반 대리 추정치만 가능. 보정 계수·고급 예측 모델 도입 근거 없음 |
| 운영 합의 | 데이터 패키지 실행 위치, JSON 전달 방식, 갱신 주기/권한 | 프론트가 Python을 직접 실행할 수 없음. 현재 HTTP 추천 endpoint는 없음 |

먼저 기존 participants API와 occupancy API를 재사용하면 됩니다. 위 요청은 추가 API 구현 완료를 전제로 하지 않습니다. analytics/daily는 버튼 기록 통계이며 예약 평균과 혼용하지 않습니다. 추후 실제 관측 완전성이 확인되면 별도로 과거 방문 통계 기반 검증/보정을 설계할 수 있습니다.
